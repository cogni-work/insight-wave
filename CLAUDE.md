# insight-wave

8-plugin monorepo for consulting, sales, and marketing on Claude Code. Apache-2.0. All plugins follow the Claude Code plugin standard. The roster and its count are single-sourced from `.claude-plugin/marketplace.json` `plugins[]` — when the roster changes, update every count stated elsewhere in this repo from it.

### Generated documentation artifacts

The repo-wide documentation-drift audit belongs at `docs/audit-report.md` — that is the single home for audit output, and it is replaced wholesale by a fresh `cogni-docs` audit run rather than hand-edited. A stale header there means the audit is due to be re-run, not patched by hand. `.claude-plugin/` holds the marketplace manifest and nothing else. An older drift report once sat at `.claude-plugin/doc-audit-report.md` and was removed rather than regenerated: nothing in this repo referenced or wrote that path, `docs/audit-report.md` supersedes it, and its plugin roster predated the current marketplace by several retirements. Do not add a report back under `.claude-plugin/`.

Not all of `docs/` is regenerated, and one file there is neither generated nor maintained. `docs/relicensing/vendored-license-audit.md` is a **frozen attestation**: it records the repository as of its stated audit date, so its findings are history and are deliberately not reconciled against the current tree. Do not hand-patch paths, names or counts inside it when an absorption or a relocation moves an asset it names — update the repo-root `NOTICE`, which is the live third-party attribution surface, and leave the attestation as written. The absorption-side statement of the same rule lives in `docs/contributing/plugin-absorption-slicing.md`.

A third boundary runs the other way, and it cannot be closed from inside this repo. `docs/plugin-guide/{name}.md` is generator output, but the generator — `cogni-docs` — ships from a separate repository and has no directory in insight-wave, so its templates cannot be corrected by any diff here. The guard is local instead: `cogni-workspace/tests/test-layering-claim-reconciled.sh` case `L1` fails if the retired dependency-order wording about `cogni-workspace` reappears in any tracked file outside that suite's own `EXCLUDED` list. Read an `L1` failure that follows a docs regeneration accordingly — it means the upstream `cogni-docs` template still emits the retired wording, not that this repo regressed. The remedy has two halves and needs both: correct the regenerated file in place, which is what returns the build to green and is what was already done once for `docs/plugin-guide/cogni-workspace.md`; and raise the fix upstream in the repo that ships `cogni-docs`, because until the template changes the next regeneration reintroduces the wording and the in-place correction has to be reapplied. Never resolve it by adding the file to `EXCLUDED` — that retires the guard instead of the claim. The canonical replacement wording is the hand-written, regeneration-stable prose at `cogni-workspace/README.md:7,24`: cogni-workspace owns the shared workspace state horizontally, while each vertical plugin keeps its own project lifecycle. Restate the guide from there rather than inventing new phrasing.

The same boundary has a second, narrower instance on the same page, and it is guarded separately. The retired `narrative-review` skill, command and agent were corrected out of `docs/plugin-guide/cogni-workspace.md` in place, but the upstream `cogni-docs` template still emits them at **two** sites, and a regeneration reintroduces both: the **capability paragraph** that presents `narrative-review` as a live capability — whose heading carries no leading slash — and the plugin's **`Commands:` line**, which lists `/narrative-review`. Cases `L11`-`L14` in `cogni-workspace/tests/test-layering-claim-reconciled.sh` are the guard behind this record: they scan that one page for the bare `narrative-review` literal, which subsumes the slash form, so both sites are caught. That arm is deliberately **page-scoped and does not consult the suite's `EXCLUDED` list at all** — `narrative-review` is live, correct prose in `cogni-workspace/references/retired-trigger-phrases.tsv` and `docs/architecture/loop-health-map.md`, so a repo-wide literal would flag the retirement's own records, and exempting the page would retire the guard instead of the claim, which the paragraph above forbids. Not consulting `EXCLUDED` is what makes that rule structural rather than a promise. The needle is fail-closed: because the page is generator output, even a hand-written past-tense retirement note naming `narrative-review` turns it red. That is intended — the remedy stays the two halves, correct in place and raise the template fix upstream, never a weakened needle.

## Cross-Plugin Conventions

### Script Output Format

All scripts return JSON: `{"success": bool, "data": {...}, "error": "string"}`. Scripts are stdlib-only — bash + python3, no pip dependencies.

### Hook Matcher Conventions

A hook matcher that matches on an **agent name** must accept the plugin-qualified `plugin:agent` form, because that is the string the host dispatches under — a plugin-supplied agent arrives as `cogni-consult:consult-dashboard-refresher`, never as a bare `consult-dashboard-refresher`. Make the qualifier optional rather than replacing the bare name, so both forms match:

```
^(cogni-consult:)?(agent-a|agent-b)$
```

Keep both anchors. The matcher is applied as a search, not a full match, so an unanchored pattern fires for other plugins' subagents too.

A bare-name-only matcher fails **silently**: the hook simply never runs, the script it would have called stays correct, and hook scripts exit 0 on every path — so nothing anywhere raises. The only evidence is the absence of whatever the hook injects. Nothing will report this class of bug for you, and no guard script checks matchers today — so when you add an agent-name matcher, pin both name forms in a suite under the plugin's `tests/`, which CI does run (see Contributing).

### Agent Model Strategy

| Role | Model | Rationale |
|------|-------|-----------|
| Orchestration | sonnet (skill context) | Phase dispatch, sub-question generation |
| Research | sonnet | Web research, section researchers, deep researchers |
| Heavy synthesis | opus | Demanding rewrites (the `copywriter` skill), 60-candidate scoring (cogni-trends) |
| Quality assessment | haiku | High-volume rubric evaluation (3-5 dimensions per entity) |
| Content generation | sonnet | Narrative writers, report writers, content writers |

Research agents report `cost_estimate` in output JSON (input/output words + estimated USD). Orchestrators accumulate these.

### Three-Layer Quality Gate

Most entity-producing plugins follow this pattern:

1. **Structural validation** — scripts check JSON schema compliance
2. **Quality assessment** — LLM-based haiku agents evaluate content dimensions
3. **Stakeholder review** — LLM agents simulate 3 reader perspectives; verdict: accept/warn/fail

Quality gates block downstream generation when upstream entities fail.

Key integration patterns:
- **Claims propagation**: Research agents auto-log claims with `entity_ref` provenance to `cogni-claims/claims.json`. After verification, corrections propagate back to entity files and cascade staleness downstream.

- **Theme inheritance**: All visual plugins read theme from cogni-workspace via `manage-themes` Operation 11 (Select Theme). Design-variables pattern produces themed CSS custom properties.

## Version Management

**Do not bump a version in a feature branch.** The patch bump is applied post-merge, automatically, per plugin actually touched.

- Plugin version lives in `.claude-plugin/plugin.json` `version` field (semver), mirrored on the plugin's entry in the repo-root `.claude-plugin/marketplace.json` — Claude Desktop reads the marketplace copy for update detection, so the two must always agree
- `.github/workflows/cogni-version-bump.yml` owns the bump. On every push to `main` it patch-increments each plugin the merge touched, editing **both** manifests in one `bump(...)` commit. `scripts/apply-version-bump.py` does the edit; nothing is written unless the rewritten JSON re-parses and differs *only* in the intended version values
- A feature branch that still touches a version reintroduces the merge-conflict class the post-merge move eliminated: when every PR bumped at authoring time, the instant one PR merged, every other open PR's version lines became a textual conflict. insight-wave had it worse than a one-manifest-per-plugin repo, because marketplace.json is a single file all 8 plugins share — so the conflict was repo-wide, not per-plugin
- `scripts/check-version-bump.py` enforces this at PR time (CI: "Version-bump gate" in `.github/workflows/lint.yml`). It flags `version-touched` on any version change vs the fork point, and `version-mirror-desync` whenever plugin.json and marketplace.json disagree. Fix a `version-touched` finding by reverting the version line in **both** files
- The auto-bump is patch-only and structurally cannot cross a maturity boundary, so `maturity` and the maturity keyword in `keywords[]` are never touched by it. **Boundary crossings stay human** — make them on a `bump/…` branch, which the PR-time gate exempts

### Plugin Maturity Model

Maturity is **hard-derived from the version** — no manual maturity field in plugin.json. Full reference: `cogni-docs/references/maturity-model.md`.

| Stage | Version Range | User Expectation |
|-------|--------------|-----------------|
| **Incubating** | `0.0.x` | Skills may change or be removed at any time |
| **Preview** | `0.x.x` (x≥1) | Core skills defined but may change. Feedback welcome |
| **Released** | `1.x.x` | Stable API. Breaking changes only at major bumps |
| **Established** | `2.x.x+` | Proven, deep ecosystem integration |
| **Archived** | Any + `"archived": true` | Security patches only |

**Maturity boundary crossings**: Bumping from `0.x` to `1.0.0` transitions a plugin from Preview to Released — this is a stability contract. Bumping to `2.0.0` signals Established. Be intentional about crossing these boundaries.

**README callout**: Each pre-1.0 and archived plugin has a maturity callout blockquote after the H1 title (e.g., `> **Preview** (v0.x) — core skills defined but may change.`). doc-generate injects this automatically. doc-audit Check 13 enforces consistency.

**No plugin ships a `.mcp.json`.** A checked-in declaration asserts machine state the repo cannot guarantee: the server is spawned at session start even where it was never installed, and it fails visibly there. A second plugin declaring the *same* server name is worse than redundant — the client disambiguates by plugin-qualifying the tool names, which silently dead-matches any `mcp__<server>__.*` hook matcher, with nothing in CI reporting it. `cogni-workspace/tests/test-mcp-declaration-hygiene.sh` enforces the rule.

## Contributing

- CLA required on first PR to core plugins (CLA Assistant bot prompts on PR)
- Feature branches from `main`; one feature or fix per PR
- Do **not** bump `plugin.json` / `marketplace.json` versions in the branch — the post-merge workflow applies the bump (see Version Management)
- Validate skill names with `cogni-workspace/scripts/check-skill-names.sh` before PR
- Plugin and repo-root `tests/*.sh` are CI-enforced — `scripts/run-plugin-tests.py` (CI: "Plugin test suites (discover and run tests/*.sh)" in `.github/workflows/lint.yml`) discovers `tests/*.sh` and `*/tests/*.sh` and fails the build on any non-zero exit. Run the full sweep locally with `python3 scripts/run-plugin-tests.py`, or one plugin's with `--filter <plugin>`. A suite only needs to exit non-zero on failure, run as `bash <path>` with no arguments, and touch no network — the runner reads exit status and nothing else. The no-suites-is-a-failure rule keys on the **pre-filter** discovered population: a discovery that finds nothing means the globs stopped matching and still exits 1 — a floor that holds even when `--filter` is supplied — while a `--filter` narrowing a real discovery down to nothing is an empty query and exits 0 with `data.total: 0`. Two plugins ship no `tests/` of their own — `cogni-marketing` and `cogni-sales` — so filtering to one of them is an ordinary empty result; never answer it with a filler suite that asserts nothing. A second consumer reads the same condition differently, and retiring a plugin's last suite must account for it: the handoff preflight in the managed-service repo derives its per-plugin floor **from the base ref**, so it is the *transition* that trips, not the end state. The PR that removes a plugin's final suite is blocked once, and is cleared with the global `COGNI_PREFLIGHT_MIN_SUITES` lever — deliberately global, so the waiver is conscious rather than scoped and standing. Once that PR is on `main` the plugin's derived floor is 0, the named `no_suites_at_base` skip applies, and subsequent PRs touching it pass unblocked, exactly as they already do for `cogni-marketing` and `cogni-sales`. So the cost of a retirement is one conscious lever use on the transition, not a standing tax on that plugin's contributors
- Keep maintainer breadcrumbs out of SKILL.md / agent files — `scripts/check-breadcrumbs.py` (CI: "Maintainer-breadcrumb guard" in `.github/workflows/lint.yml`) fails on newly introduced issue/PR refs (`#NNN`), version tags, or milestone/slice/finding codes. It ratchets against `scripts/baselines/breadcrumb-baseline.json`, so only *new* breadcrumbs trip it; fix by removing the breadcrumb and stating the rationale semantically (provenance lives in git history, CHANGELOG, and `references/`)
- Every `.github/workflows/*.yml` and `*.yaml` must load and declare jobs — `scripts/check-workflow-yaml.py` (CI: "Workflow-YAML guard (every .github/workflows file parses)" in `.github/workflows/workflow-guard.yml`) flags an unquoted plain scalar carrying a colon-space (the shape that makes a file unparseable, silently taking *every* job in it offline rather than failing one step) and a file that declares no jobs. Stdlib-only, no pip dependency; suite at `tests/test_check_workflow_yaml.sh`. It lives in its own workflow on purpose — a guard hosted inside `lint.yml` could never report `lint.yml` failing to load, because the job holding it would not run either
- No discovered test suite may emit an escape-wrapped `PASS:`/`FAIL:` result line — `scripts/check-result-line-plainness.py` (CI: "Result-line plainness guard (no escape sequence in discovered suites)" in `.github/workflows/lint.yml`) flags an escape literal anywhere in a `tests/*.sh` or `*/tests/*.sh` file, and separately flags a `red()`/`green()`-class emitter defined with a coloured body *even when its call-site label lines are clean* — the copy-an-emitter-into-a-new-suite path. A colour before the label defeats a mutation harness's `^[[:space:]]*FAIL:[[:space:]]+<case>` match, so a genuinely red case reports `case_not_found`. Fix by writing the emitter to `printf '%s\n' "$1"`, never by gating it on a capability probe (that makes parsability depend on where the suite runs, and the colour returns under a pty). Hard clean zero — no baseline, allowlist or skip marker; suites parked one path segment deeper are out of scope by glob depth, not by exclusion. Stdlib-only; suite at `tests/test_check_result_line_plainness.sh`
- Every invocation-shaped mutation recipe in `tests/*.sh` and `*/tests/*.sh` must name the unversioned managed-service marketplace harness — `scripts/check-mutation-recipe-harness.py` (CI: "Mutation-recipe harness guard (recorded paths use the stable marketplace install)" in `.github/workflows/lint.yml`) rejects version-pinned cache paths, repo-root imports, placeholders, checkout-local paths and pathless spellings. Detection keys on invocation shape and continued recipe flags, so prose about the separate plugin-local harnesses remains outside the population without an allowlist. The guard's module docstring owns why cache pins rot and why CI asserts spelling rather than local resolvability; do not re-derive those mechanics here. Zero discovery is an error and the invariant is hard clean zero — no baseline, allowlist or skip marker. Stdlib-only; suite at `tests/test_check_mutation_recipe_harness.sh`
- Every `FAIL: <id>` arm in a discovered test suite needs a reachable same-id green twin (`PASS:` or `ok:`) — `scripts/check-case-id-pairing.py` (CI: "Case-id pairing guard (every FAIL arm has a same-id green twin)" in `.github/workflows/lint.yml`) flags a fail-only case id, because a case whose green arm can never print emits nothing on a green run, so `mutation-check.sh --case <id>` reports `case_not_found` on a genuinely red run and the guard that case was written to prove is left proving nothing. It resolves one level of helper indirection: the dominant emission shape here puts the label in a `fail()`-class definition and the id at the call site, so a same-line literal scan sees `$1` rather than the id and would ship green and dead over every suite built that way. Do not re-derive the rest here — the guard's own module docstring owns which fail-only arms it exempts and why, the recall floors it deliberately accepts, and the measured population behind them; a second copy in this file is a second thing to drift, and the measurement is a snapshot the next suite invalidates. Stdlib-only; suite at `tests/test_check_case_id_pairing.sh`
- An agent body may only call MCP tools its own frontmatter grants — `scripts/check-mcp-tool-grant.py` (CI: "MCP agent-grant guard (agent bodies call only servers their frontmatter grants)" in `.github/workflows/lint.yml`) asserts repo-wide that every affirmative `mcp__<ns>__<tool>` token in an agent body is granted by that agent's `tools:` frontmatter, and that every plugin granting a *registered* namespace appears in that server's `required_by`. Detection keys on an **affirmative call site, never prose**: agents elsewhere DISCLAIM a server in the same phrasing ("no Excalidraw MCP"), so a `<X> MCP` heuristic reads them as offenders on day one. It parses all three `tools:` forms — bracketed array, bare comma list, and YAML block list; the block form is load-bearing, not a nicety, because most agents carrying a real call site declare tools that way and a `tools:`-line-only reader reports them as false offenders. The namespace token class admits **hyphens** — real namespaces here are spelled `claude-in-chrome`, and an `[A-Za-z0-9_]`-only class matches none of `mcp__claude-in-chrome__navigate`, going blind to a whole namespace with every case still green. A **second affirmative arm** is keyed on the registry's `provides_tools[]`: an agent body naming a registry tool's bare name **inside a backtick code span** must grant a tool of a server that provides it, resolved at server level. The code span is the mechanical context requirement — bare names like `get_screenshot` and `export_scene` are ordinary English, so matching them in running prose is the false-positive class that once kept a prose heuristic plugin-scoped. This arm **replaced** that plugin-scoped prose detector rather than joining it, which is why no second scope or second suite survives. Do not re-derive the arm's rules here: the guard's own module docstring owns the mechanism, the measurement behind the adoption, and the residual classes it knowingly does not cover — a second copy in this file is a second thing to drift, and the measurement is a snapshot that the next registry entry invalidates. Registry-accuracy gaps take a **non-failing** channel and never move the exit code: a granted `mcp__<registered-ns>__<tool>` whose bare name is absent from that server's `provides_tools[]` is surfaced as an observation, while a registered server carrying no `provides_tools[]` at all is an **error** rather than a narrowed vocabulary — the docstring owns why the two differ. Zero discovery is a failure, not a clean zero. Hard clean zero — no baseline, allowlist or skip marker; suite at `tests/test_check_mcp_tool_grant.sh`
- Every repo-relative path a **live attribution surface** claims must resolve in this repository's tracked index — `scripts/check-attribution-path-integrity.py` (CI: "Attribution path guard (every path a live attribution surface claims resolves)" in `.github/workflows/lint.yml`) resolves each claim through `git ls-files` rather than the filesystem, so a wrong-case path that passes on a case-insensitive clone still fails on case-sensitive CI, and a claim naming an untracked or gitignored file is a finding rather than a pass — the honest property for a record that has to resolve in a fresh clone. The unit is the class of files this repo maintains as a *current* record of third-party credit, never narrative link rot: a broken prose link is an editorial problem, a broken attribution path is a licensing-compliance one, and only the second is a blocking gate's business. Discovery follows a naming-and-location convention rather than a register, so a new plugin's license file is covered the moment it lands with nothing to edit. Do not re-derive the rest here — the guard's own module docstring owns which surface names and locations it discovers, why a dated frozen attestation is out of class structurally rather than by filename, the two carriers a claim can arrive through and the shape tests that exclude a URL or a bare filename, and the recall floors it deliberately accepts; a second copy in this file is a second thing to drift. Zero discovered surfaces is a failure rather than a clean zero. Hard clean zero — no baseline, allowlist or skip marker, in either direction; stdlib-only; suite at `tests/test_check_attribution_path_integrity.sh`
- Every per-plugin skills/agents count the **root** `README.md` states must equal a live count of that plugin's `skills/*/SKILL.md` and `agents/*.md`, and the roll-up must equal their sums — `scripts/check-readme-inventory-sync.py` (CI: "README inventory-sync guard (root README counts match live directories)" in `.github/workflows/lint.yml`). Each plugin states its counts in three linked places — the prose paragraph, the "Plugins at a glance" row, and the roll-up total — so a retirement that sweeps one leaves the file contradicting itself, and sweeping none is what happened: the plugin's own README was corrected while the root's duplicate of the same number was bound by nothing. The marketplace-to-directory bijection guard asserts *inventory*, never counts, so the repo suite stayed green over the stale line. Claims are read only inside their anchoring H2 section, never file-wide, so a second pipe table elsewhere in the README can never be mistaken for a claim — and a renamed anchor heading is a violation rather than a silent zero-discovery. Rows are keyed by the plugin name in each row's link text and the count cells are located from the table's own header row, never by position: the table's row order and the manifest's `plugins[]` order differ, and its column set is not stable either. Note the one external dependency — this README is a generated artifact reassembled by a documentation generator in the `managed-service` repo, so the anchoring headings are that generator's canonical section names, and a regeneration that drops a plugin's count sentence lands here as `prose-claim-missing` rather than silently.
