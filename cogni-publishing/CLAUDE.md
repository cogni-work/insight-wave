# cogni-publishing

Standalone publishing contracts and validation for insight-wave. The plugin must work without cogni-workspace — or any other insight-wave plugin — being installed or initialised.

## Architecture

The artifact chain is deliberately split so each stage evolves on its own version:

1. authored input — `direct-brief@1`, or the bounded `design-brief@1.1` slides adapter
2. `normalized-brief@1` — the only place copy and data live
3. `semantic-composition@1` — grouping and roles, by reference
4. `target-resolved-plan@1` — target and design-system decisions, by reference

Beside that chain, `design-compose` binds a normalized brief to `pattern-library@1` — the bundled `references/pattern-library-v1.json` — and emits a `semantic-composition@2`: pattern-bound units that reference content by id and digest and carry no copy and no target geometry. `target-resolved-plan@1` still consumes `@1` only. `design-render` lays a `@2` composition out as a `target-resolved-plan@2` — geometry and typography per slot, content by the composition's own references — and renders it. Its layering: `scripts/design-render.py` is the stdlib wrapper and the only entry point, `scripts/render_core.py` the target-neutral core (inputs, theme, fonts, plan, provenance), and each target is a sibling adapter behind them with its own independent checks — `scripts/html_adapter.py` with `scripts/render_checks.py` for `html`, and `scripts/pptx_adapter.py`, a stdlib Office Open XML writer, with `scripts/pptx_checks.py` for `pptx`. A deck is written straight from the plan and records every object's editability in a `pptx-manifest@1`; neither adapter imports the other. `references/design-render.md` is normative for the render.

`references/artifact-contracts.md` is normative for the chain and `references/design-composition.md` for the pattern contract and binding rules; the JSON Schemas beside them document the same shapes. `scripts/validate-publishing.py` is the single enforcer.

## Conventions

- Scripts use Python 3 stdlib only and emit exactly one `{"success": bool, "data": {...}, "error": string|null}` on stdout and nothing on stderr. Exit 0 valid, 1 contract rejection, 2 usage/runtime error. A rejection's `data` is the finding (`code`, `check`, `artifact`, `reference`) and never a partial artifact.
- Never copy text into a downstream artifact. Composition and plan units reference normalized records by id; the validator rejects any other unit field as `unexpected-field`.
- Normalization never rewrites, reorders or drops a value. Narrative records keep their exact source slice as `raw`.
- The narrative adapter stays bounded to the slides grammar of `design-brief@1.1`. Widening it to another target or version is a contract change, not a parser tweak.
- A direct brief keeps its declared `structure`; never add arc, BLUF, slide-number or narrative-element requirements to it.
- Read workspace preferences only from a caller-supplied path. The validator never reads environment variables or the home directory and never probes sibling plugin paths; `pubc-16` in the suite enforces this with an audit hook.
- Resolve configuration per key: supplied values, publishing project configuration, optional workspace preferences, bundled defaults.
- Rendering stays optional and outside validation. An external renderer is pinned with an exact version and consumes `target-resolved-plan@1`; validation checks the pin as data and never installs, imports or runs a renderer.
- `design-render` renders both targets in Python 3 stdlib, and the render path — the PPTX writer and its checks included — must compile on Python 3.9, the repo's floor — so no nested same-quote f-strings, `match` statements or runtime `X | Y` unions. Its browser runtime under `runtime/` only measures a page, is pinned by `runtime/package-lock.json` (exact versions, sha512 integrity), is provisioned only by running `runtime/provision.sh` — once per machine by an operator, or in CI by its own step of the Plugin test suites job ahead of the sweep — and is resolved only from its provisioning record: never from PATH, and never installed by the wrapper, a skill or a suite. Keep `npm`, `npx`, `pip` and `curl` out of the wrapper and render path.
- Every original string reaches the page through the adapter's one insertion function, `text()`, whose body must stay exactly `return escape(value, quote=True)` — the recorded `drnd-10` recipe mutates that line. Attribute values use `attr()` instead, so the recipe hits copy only.
- The PPTX writer has the same shape: every original string reaches the package through `xml_text()`, whose body must stay exactly `return escape(value)` and occur once in `pptx_adapter.py` — the recorded `drpx-06` recipe mutates it — and attribute values use `xml_attr()`. The native chart is placed by the single call line `shapes.append(self.native_chart(unit, slot, entries))`, and `self.native_chart(` must occur exactly once in the file, because the recorded `drpx-09` recipe swaps it for `self.data_table(`.
- A deck never shrinks, splits, merges, truncates or reorders a unit to fit its fixed slide: a frame the plan grew past 720 px fails as `fit-overflow`, copy a package cannot hold fails as `unsupported-content`, and no text body carries `a:normAutofit` or a `fontScale`. A picture may enter a deck only as a fallback its unit's pattern declares for pptx, recorded in the manifest.
- The render validates everything, runs the fidelity checks on its own page, and only then writes; a rejection writes nothing. Never patch a rendered page, plan or provenance by hand — re-render from the inputs.
- Component CSS in the adapter uses theme tokens through `var()` only, and nothing may hide, clamp or clip copy. A theme may ship licensed faces, declared in its `assets/fonts/faces.json`: the html target embeds the copy face as an `@font-face` data URI ahead of the token block — the single `url()` the portability check admits, and only when its bytes equal the file the theme ships — while a deck embeds no font. Any other face resolves to a generic chain in `references/font-fallbacks-v1.json` and is recorded as a substitution; `bundled_faces` stays empty, because a face ships with the theme that uses it. A font file enters the tree only with its licence beside it and a root `NOTICE` entry whose `Location:` and `See:` lines resolve.
- Add a contract version only with a compatibility row in `references/artifact-contracts.md` and the matching `SUPPORTED`/`COMPATIBLE` entries in the validator, in the same change.
- Patterns are library data; families (`text`, `chart`, `system`, `register`) are validator code. Adding a pattern is a library entry with at least one passing specimen; adding a family is a reviewed code change.
- A `proposed` pattern never reaches production: the composition commands reject it as `unaccepted-pattern`. Promotion is a reviewed change that flips its `status` once `check-patterns` reports it ready.
- `compose` fills only mechanical fields — digests, the content fingerprint, citations, the register and trailer-note bindings — and never picks, splits, merges, truncates or reorders content. A repair changes only pattern, variant and slot names.
- The composition commands read the bundled library beside the script, found from the script's own location, or an explicit `--patterns` file — nothing else.

## Theme lifecycle

This plugin is the single owner of the theme lifecycle: `manage-themes` (selection, authoring, audit, showcase, application and Claude Design import), the bundled `themes/`, and the scripts, schema and references behind them. `cogni-workspace` keeps only compatibility routes — a same-name `manage-themes` skill that delegates here and four script entry points resolved through its `scripts/_publishing_delegate.py` — so never add theme behaviour there; add it here and let the routes forward it.

- **Roots come from the script's own location.** The theme scripts find the bundled `themes/` as `<plugin>/themes` relative to themselves, with `--plugin-root` as an explicit override. They never read `$CLAUDE_PLUGIN_ROOT` for it: a caller in another plugin — or a delegate — runs with that variable naming a plugin that ships no themes.
- **User themes are input, never output of a read.** The optional user location resolves `--user-themes` > `--workspace-root`/themes > `$COGNI_WORKSPACE_ROOT/themes` > legacy auto-discovery (`discover-themes.py` only), and a user theme shadows a bundled one of the same slug. No read moves, rewrites or creates anything there; only the write operations of `manage-themes` do.
- **The selection handoff is `theme_path` / `theme_name` / `theme_slug`**, emitted by `scripts/select-theme.py` and defined in `references/theme-artifact-contract.md`. Its explicit-path mode reads no environment and nothing under `$HOME`.
- **Legacy output shapes are part of the contract.** `discover-themes.py` prints a bare JSON array with `standard`/`workspace` source labels, and its tier-0 output is snapshotted in `scripts/baselines/`; `inspect-themes.py` and `check-theme-drift.py` keep their envelopes. The envelope-only, nothing-on-stderr rule above binds the contract scripts and `select-theme.py`; the legacy theme scripts keep their existing stderr hints.
- **`tokens/*.json` is the one authoritative token representation.** `generate-tokens-css.py` compiles it to `tokens.css` (aliases stay `var()` references) and, when an alias exists, `tokens.resolved.json`. Both are projections: regenerate them, never edit them. The token header line and flat-map output are frozen, because every saved `tokens.css` is parity-checked against them. The accepted input shapes are `references/token-subset.md`; a `$type` added to the compiler's `SUPPORTED_TYPES` must be added to that page's `**Supported $type values:**` line in the same change, which `stok-19` pins.
- **A tier-0 theme's tokens are derived, never transcribed.** `scripts/derive-theme-tokens.py` writes `colors.json`, `typography.json` and `spacing.json` from a `theme.md` — every value verbatim from its row, no default and no hex of its own — and has the compiler write `tokens.css`. The `boardroom`, `clean-slate`, `editorial` and `signal` presets ship that output, so after editing one of their `theme.md` files re-run `derive-theme-tokens.py themes/<slug> --overwrite`; never edit their token JSON. The renderer keeps reading only `tokens/*.json`: a role a `theme.md` lacks stays absent and fails as `theme-token-missing`, and nothing in the render path parses `theme.md` prose or fills a role. Without `--overwrite` the derivation refuses any target that already holds token files, which is what protects `cogni-work`'s imported tokens.
- **The importer never writes around a broken graph.** A bundle alias cycle or unresolved reference aborts before the target is touched; unsupported alias forms are reported in `aliases_dropped`, never dropped silently. Re-import replaces only the files the sidecar's `managed_files` lists.

## Tests

`tests/test-publishing-contracts.sh` is discovered by `scripts/run-plugin-tests.py`. Case ids are `pubc-NN-<discriminator>`, allocated once and never renumbered — the mutation recipes in the suite header and README record `pubc-04-invalid-version` and `pubc-05-dangling-reference`. The two predicates those recipes mutate, `version_supported` and `reference_resolves`, must keep their exact one-line bodies, or the recorded `--expr` stops matching.

`tests/test-design-compose.sh` grades the composition layer with `dcmp-NN-<discriminator>` ids under the same allocate-once rule. Its recorded recipes mutate `order_preserved`, `provenance_present` and `pattern_accepted` in the validator, which must keep their exact one-line bodies — `return positions == sorted(positions)`, `return len(source_refs) > 0` and `return pattern.get("status") == "accepted"` — the register guard in `validate_composition`, which must stay the single line `if require_register and index.source_ids and not state.register_units:` — and the routing sentence in `skills/design-compose/SKILL.md` that begins "Never route a proposed pattern into a production composition", which must occur exactly once. `pubc-16` also audits the four composition commands for standalone isolation. The two composition fixtures are frozen `compose` output: regenerate them with `compose` from a stripped draft, never by typing a digest.

`tests/test-design-render.sh` grades the render with `drnd-NN-<discriminator>` ids under the same allocate-once rule. Its four recorded recipes mutate the adapter's `text()` body, which must fail `drnd-10-frozen-copy`; the single line `if node.tag == "style":` in `render_checks.py`'s `reference_surfaces`, which must fail `drnd-37-prose-paths-render`; and the two embedded-face gates in `render_checks.py`, `if shipped_family != family:` and `if face is None or face["format"] != form or face["mime"] != mime:`, each of which must fail `drnd-50-embedded-face-negatives` — so each of those three lines must keep its exact text and occur once in the file. Its expected strings come from the fixture inputs through the suite's own html.parser reader, never from a render; a case that needs an edited brief recomposes from a stripped draft with `compose`. `drnd-34`, `drnd-35` and `drnd-53` need the pinned runtime: without it they print `SKIP:` naming the absent runtime and never `PASS:`. `drnd-36` compiles the render path with the oldest Python 3.9–3.11 interpreter on the host and prints `SKIP:` when there is none. The Plugin test suites job in `.github/workflows/lint.yml` provisions both in their own steps before the sweep — the runtime by running `runtime/provision.sh`, and a Python 3.9 exposed as `python3.9` beside the runner's newer `python3` — and sets `COGNI_PUBLISHING_REQUIRE_PROVISIONED=1`. Under that variable each of those `SKIP:` arms prints `FAIL:` under the same id, so CI cannot go green with them skipped; a local run without it keeps the `SKIP:` arms. `drnd-02`, `drnd-03`, `drnd-04` and `drnd-36` name the render-path files one by one, the PPTX modules among them, so a new render module joins those lists or escapes their guards; `drnd-31` proves an unowned target is refused. The render fixtures live in `tests/fixtures/render/`: `composition-direct-de-edge-v2.json` is frozen `compose` output under the same regenerate-never-type rule; `themes/cogni-work/` is a fixed copy of the test theme, so captured geometry never moves with the bundled theme; and `plan-narrative-captured-v2.json` is a captured render of the narrative fixture with that theme — regenerate it only by rendering, and only when the layout rules change on purpose. `font-theme/cogni-work/` is that theme with one change, a copy font that leads with Outfit, which it ships under `assets/fonts/` beside its `OFL.txt`; it is the only font binary in the tree, the root `NOTICE` names both files by path, so moving either means moving those `Location:`/`See:` lines with it, and a case that needs a variant copies the theme into a scratch directory rather than committing a second binary. Its declared `advance_em` is derived from the file, and `drnd-49` re-derives it from the TrueType tables.

`tests/test-design-render-pptx.sh` grades the PPTX target with `drpx-NN-<discriminator>` ids under the same allocate-once rule, and is also the documented capability test behind the stdlib writer that replaces PptxGenJS. From the package itself it proves each of the five pptx capabilities pattern-library@1 declares: `text-frame` by `drpx-06-frozen-copy`, `hyperlink` by `drpx-13-citations-and-order`, `editable-shapes` by `drpx-11-editable-shapes`, `native-chart` by `drpx-09-native-chart` and `speaker-notes` by `drpx-12-notes-evidence`. That mapping is stated normatively in `references/design-render.md`; keep every copy of it listing all five. Its two recorded recipes mutate `xml_text()`'s body, which must fail `drpx-06-frozen-copy`, and the `self.native_chart(` call, which must fail `drpx-09-native-chart`. Its expectations come from the fixture inputs through the suite's own zipfile/ElementTree reader, never from a render and never through `pptx_checks.py`; its negatives are doctored copies of a green deck. Two of those rules are easy to weaken by accident. The readability floor is per slot: `pptx_checks.py` resolves each copy shape's type role from the composition, the pattern library and the theme through `render_core`'s `SLOT_ROLES` and `TYPE_ROLE_TOKENS` — never from the writer — and keeps the caption size only as a backstop, which `drpx-17`'s shrunk-headline negative distinguishes from the per-slot rule. And a picture is rejected as `unreported-flattening` on three separate arms — no manifest entry, an entry claiming native editability, a fallback entry without capability or reason — each with its own `drpx-14` negative, so dropping one clause turns that case red. Rendering a deck needs no runtime, so the suite has no `SKIP:` arm: every case runs wherever the suite runs, CI included. `docs/pptx-smoke-evidence.md` records the application open and edit evidence CI cannot produce. It labels a check no person has performed yet as pending rather than omitting it, and no other surface may claim an application result that file does not record.

The narrative fixture is cogni-workspace's green `slides-en.md` design brief plus one `evidence_status` line on slides 2–6; its expected normalized output is frozen in `narrative-slides-v1.expected.json`. When the adapter's output shape changes on purpose, regenerate that file and confirm `pubc-02` — the independent slicing oracle — still passes before committing it.

The theme suites follow the same id discipline: `test-theme-lifecycle.sh` (`thl-NN-…`), `test-semantic-tokens.sh` (`stok-NN-…`), and the moved `test-theme-backcompat.sh` (`tbc…`), `test-bundled-presets.sh` (`bp-…`) and `test-check-contrast.sh` (`cc…`). The alias recipe in the `test-semantic-tokens.sh` header mutates `retains_alias` in the importer, so that function must keep its exact one-line body, `return ALIAS_VAR.fullmatch(value) is not None`.

`tests/test-derive-theme-tokens.sh` grades the tier-0 derivation and the bundled themes it makes renderable with `dtt-NN-<discriminator>` ids under the same allocate-once rule, each per-theme id carrying the theme slug. Per preset it re-derives the committed `theme.md` into a scratch directory and byte-compares every token file (`dtt-03`), and checks idempotency, renderer-role coverage, verbatim literals, the Border outcome and font order; for all five bundled themes it runs a real `render --target html` and reads the font records in provenance; it also covers the missing-role fixture in `tests/fixtures/derive/`, the refusal to overwrite existing tokens, malformed and repeated rows and heading scope. Its oracles read `theme.md` with their own section slicer, never the derivation's parser. The recorded recipe mutates `"Background": "bg"` in `derive-theme-tokens.py`, which must fail `dtt-03-rederive-boardroom`, so that substring must occur exactly once in the file.
